# Data Models

## Model Layers
- `vod_job` is the user-facing aggregate for one submitted VOD.
- `worker_task` is the operational work unit queued for backend-to-worker orchestration.
- `worker_execution` is one concrete worker attempt against one claimed task.
- `clip_candidate` is the review/export entity produced by analysis.
- `artifact` is the durable storage reference layer used by backend and workers.

## vod_job
Represents the aggregate lifecycle of one VOD from intake through review and export visibility.

Fields:
- id
- source_type
- source_url
- original_filename
- status
- processing_version
- progress_percent
- progress_message
- current_worker_id
- last_worker_heartbeat_at
- created_at
- updated_at
- started_at
- finished_at
- error_message
- duration_sec
- language
- storage_video_path
- storage_audio_path

Notes:
- `vod_job` is not the primary runtime execution record.
- `vod_job.status` is a projection of task/execution progress for UI and operators.
- operator retry increments `processing_version` so stale worker callbacks can be rejected cleanly.

## worker_task
Represents one backend-managed task in the execution queue.

Fields:
- id
- job_id
- processing_version
- task_type
- status
- candidate_id
- created_at
- updated_at
- claimed_at
- last_heartbeat_at
- finished_at
- failure_message

Current task types:
- DOWNLOAD
- ANALYZE
- EXPORT

Current task statuses:
- QUEUED
- CLAIMED
- RUNNING
- SUCCEEDED
- FAILED
- CANCELED

Notes:
- one `vod_job` may produce multiple `worker_task` rows across its lifecycle
- `EXPORT` tasks may target one `clip_candidate` through `candidate_id`
- the active queue contract is task-centric even if some API names still include `job`

## worker_execution
Represents one concrete worker claim/attempt for a task.

Fields:
- id
- job_id
- task_id
- processing_version
- worker_id
- worker_role
- task_type
- status
- candidate_id
- claimed_at
- last_heartbeat_at
- finished_at
- failure_message

Current execution statuses:
- CLAIMED
- RUNNING
- SUCCEEDED
- FAILED
- CANCELED

Notes:
- every worker callback must be tied to `execution_id`
- `worker_execution` is the authoritative record for lease ownership and callback correlation
- a task may accumulate multiple executions over time as the model grows retry/recovery semantics

## transcript_segment
Represents a persisted transcript fragment for one analyzed job.

Fields:
- id
- job_id
- start_sec
- end_sec
- text
- word_count

## silence_segment
Represents a persisted silence interval for one analyzed job.

Fields:
- id
- job_id
- start_sec
- end_sec
- duration_sec

## analysis_window
Represents one scored analysis window for one analyzed job.

Fields:
- id
- job_id
- start_sec
- end_sec
- speech_density
- silence_ratio
- emotion_hits
- continuity_score
- total_score

## clip_candidate
Represents a candidate clip generated by analysis and later moderated/exported.

Fields:
- id
- job_id
- start_sec
- end_sec
- score
- transcript_excerpt
- moderation_status
- moderator_note
- export_status
- exported_clip_path

Current moderation statuses:
- PENDING
- APPROVED
- REJECTED

Current export statuses:
- NOT_REQUESTED
- IN_PROGRESS
- COMPLETED
- FAILED

## artifact
Represents a durable backend-known artifact reference.

Typical artifact categories:
- source video
- extracted audio
- exported clip
- optional derived analysis asset

Typical fields:
- id
- job_id or candidate_id
- artifact_type
- storage_key
- storage_provider
- content_type
- size_bytes
- checksum
- created_at

Notes:
- the current codebase still stores some artifact paths directly on aggregate entities
- future work should converge on durable artifact references rather than path-only coupling

## job_event
Represents an audit/event log entry for a job lifecycle change.

Fields:
- id
- job_id
- event_type
- message
- created_at
